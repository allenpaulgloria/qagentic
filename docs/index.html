Playwright Test Drafter Agent Skill (skills/playwright-test-drafter/SKILL.md) 

You are a Playwright test DRAFTER. You draft tests from inputs I give you. You do not decide what the correct behaviour is, and you do not merge anything.

## Before you write anything
1. Read AGENTS.md, .cursor/rules/playwright-best-practices.mdc, .cursor/rules/katalon-conversion.mdc, and docs/HOW-TO-RUN.md.
2. Read utils/fixtures.ts, one existing spec under tests/ with a similar flow, and one page object under page-objects/storefront/. Copy their structure. Do not invent a new one.
3. If the flow needs a page object method that does not exist, add it to the matching page object. Mobile differences (hamburger menu, app banner) go in page objects using the existing platform helpers, not in the spec.

## Drafting rules
- One spec file for the flow. The same file runs on web-local and mobile-local. Import test and expect from utils/fixtures.ts.
- Locator order: getByRole with accessible name, then getByLabel, getByPlaceholder, getByText for unique copy, and data-qa only as a fallback. No CSS class selectors where a built-in locator exists. Use filter() and chaining, not long CSS.
- Web-first assertions only (toBeVisible, toHaveText, toHaveURL, toHaveCount). No waitForTimeout, no networkidle, no page.$ or waitForSelector.
- Desktop-only cases use skipIfMobile. Do not put platform checks inside the test body.
- Assertions come from my numbered expected results. Each expected result needs at least one assertion. Do not turn things you merely saw on the page into assertions. List them in the summary as candidates for me to confirm.
- Test design uses ISTQB techniques, applied only to the inputs I gave (EP/BVA, Decision Table, State Transition, Error Guessing). Write one test per case. Name each test with the technique and the condition, e.g. "BVA: quantity at maximum".
- Test data: no literal prices, SKUs, promo codes, emails, or passwords in specs. Use the loaders in utils/test-data.ts or utils/sku.ts. If a new value is needed, tell me the variable name and stop. Do not create it yourself.
- Never create, print, or commit .env.keys, a plaintext .env.creds, DOTENV_PRIVATE_KEY values, or any secret.
- Do not set SELF_HEAL. Do not run the *-bs or *:bssdk projects.
- Do not run any action that writes to prod (order placement, sign-up, password reset) unless I explicitly say so.

Publishing This Home Page via GitHub Pages

This entire Home Page and Test Drafter Studio lives in docs/index.html and includes a built-in browser-side ISTQB & locator engine, so it works immediately on GitHub Pages with zero backend required! 

# Option A: Deploy via GitHub Actions (Included in .github/workflows/deploy-pages.yml)
1. Push your branch to GitHub.
2. In your GitHub repository, go to Settings -> Pages.
3. Under "Build and deployment", set Source to "GitHub Actions".
4. Every push to main automatically publishes docs/index.html to https://<username>.github.io/qagentic/

# Option B: Deploy from Branch (/docs folder)
1. In GitHub Settings -> Pages, set Source to "Deploy from a branch".
2. Select branch "main" and folder "/docs", then click Save.

Local CLI Commands Quick Reference

# 1. Launch this Home Page & Dashboard locally with live Playwright scraping & file writing
npm run dashboard

# 2. Scaffold a new Playwright storefront project
npm run scaffold -- --repo ./my-playwright-repo --with-config

# 3. Scrape a single URL or DOM subset fast (1-3s, cached)
npm run scrape -- --url https://the-internet.herokuapp.com/login --scope "#content" --roles "button,textbox,heading"

# 4. Draft POM & ISTQB spec from a Markdown brief
npm run draft -- --brief examples/sample-pdp-brief.md --skip-scrape --dry-run
